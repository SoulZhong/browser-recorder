# 技术方案

本文档说明 Browser Recorder 的架构、实现取舍和测试方式。安装和使用见 [README](../README.md)，文中源码路径均相对仓库根目录。

### 1. Offscreen Document 承载 MediaRecorder

MV3 用 Service Worker 取代了常驻后台页，而 SW 没有 DOM，拿不到
`MediaRecorder` / `getUserMedia`，而且随时可能被回收。

解法是 **Offscreen Document**（`chrome.offscreen`）——一个不可见的常驻 DOM 环境：

```
popup          ──消息──►  Service Worker  ──消息──►  Offscreen Document
   (UI)                    (编排 / 权限 / 窗口)        (MediaRecorder / 混流)
                                                              │
                                                              ▼
                                                        IndexedDB (分片)
```

Service Worker 只做编排：拿 streamId、管 offscreen 生命周期、注入覆层和维护徽标。
**它被回收也不会中断录制**，因为录制状态活在 offscreen 里。

`src/background/service-worker.js` · `src/offscreen/offscreen.js`

### 2. streamId 换流

扩展 API 只给 streamId，不直接给 MediaStream；还原动作必须发生在有 DOM 的上下文里。

```js
// Service Worker：紧贴用户手势拿 id
const streamId = await chrome.tabCapture.getMediaStreamId({ targetTabId });
// 或整个屏幕：
chrome.desktopCapture.chooseDesktopMedia(['screen','window','tab','audio'], tab, cb);

// Offscreen：还原成真实的 MediaStream
navigator.mediaDevices.getUserMedia({
  video: { mandatory: { chromeMediaSource: 'tab', chromeMediaSourceId: streamId,
                        maxWidth, maxHeight, maxFrameRate } },
});
```

屏幕录制时用户可能没勾「分享音频」，带 audio 约束会整体失败——代码里做了
「先带音频试，失败再退回纯视频」的降级。

### 3. 分片写入 IndexedDB（本地存储核心）

`MediaRecorder.start(3000)` 每 3 秒吐一个 Blob 分片，**立刻落盘**：

```js
recorder.ondataavailable = (e) => {
  const seq = session.seq++;
  // 串行化，避免高码率下并发事务压垮 IDB
  writeQueue = writeQueue.then(() => appendChunk(id, seq, e.data));
};
```

这样做的三个理由：

- **内存不随时长增长** — 录 2 小时也不会把整段视频堆在内存里
- **崩溃只丢最后 3 秒** — 浏览器崩了、标签页被杀，已落盘的部分照样能播能导出
- **Blob 过不了消息通道** — `chrome.runtime` 的结构化克隆不支持 Blob，
  所以分片必须由 offscreen **直接**写库，SW 只收到轻量的字节数进度

表结构：

| store | keyPath | 内容 |
|---|---|---|
| `recordings` | `id` | 标题、模式、分辨率、时长、体积、状态 |
| `chunks` | `[recordingId, seq]` | 复合主键天然有序，读出来即拼接顺序 |

回放时 `new Blob(chunks)` 只建引用不复制数据（分片本身是磁盘背书的），
所以拼接一段 1GB 的录制几乎不耗内存。

**读-改-写必须同步发出。** `patchRecording` 在 `get` 的 `onsuccess` 里直接 `put`，
而不是 `await wrap(get)` 之后再 `put`——后者依赖「事务在 success 事件的微任务检查点里
仍处于 active」这个规范灰区，一旦续体被推迟到下一个宏任务就是 `TransactionInactiveError`。

`src/lib/db.js`

### 4. 崩溃恢复与写入失败

扩展启动时把仍标记为 `recording` 的记录收敛为 `interrupted`，按已落盘的分片
补全时长和体积；0 分片的空壳直接清理。这些片段在录制库里标注「已恢复」，可以正常播放和导出。

**时长要提前落盘。** 崩溃后用「最后一片的时间戳 − createdAt」倒推会把倒计时、
建流准备和所有暂停时间都算进去，明显偏长。所以录制中每 10 秒把真实 `elapsedMs`
写进元数据，误差压到 10 秒以内；相对 3 秒一片的视频写入，这点开销可以忽略。

**写入失败不能装作成功。** 分片落盘失败最现实的原因是磁盘/配额耗尽——它不会自行恢复，
继续录下去只会产出一段中间有洞、却被标成「已完成」的视频。所以第一次写入失败就立刻收尾，
记录标记为 `error` 并带上原因，录制库显示「写入失败」标签，控制条实时弹出提示。

**一片都没录到，也绝不能静默丢弃。** 早期版本在 `chunkCount === 0` 时直接删除记录、
不开播放页——用户点了「结束」之后什么都不发生，录制库里也空空如也，完全无从判断。
现在这条记录会保留下来，状态为 `error` 并写明原因（时间过短 / 采集源已结束 / 写入失败），
播放页照常打开。**宁可展示一条失败记录，也不要让用户面对"什么都没发生"。**

录制库页面可能在录制过程中被打开，所以 `reconcileInterrupted(activeId)` 必须
排除当前活跃的那一条，否则会把正在写入的记录误判成已中断。

### 5. WebM 时长修复

`MediaRecorder` 是流式封装，写 EBML 头的时候还不知道总时长，于是 `Segment > Info`
里没有 `Duration` 元素——播放器读到 `video.duration === Infinity`，进度条拖不动。

`src/lib/webm-duration.js` 直接改 EBML 字节：

- 已有 `Duration` → 原地覆盖浮点值，字节数不变
- 没有 → 追加 11 字节（id `0x4489` + size + float64），
  并用**等长填充**重写 `Info` 的 size 字段，从而不影响任何后续偏移

**补丁只在内存里做，绝不回写落盘的分片。** 它改的是整段视频的解码入口，
一旦打歪就是整段无法播放——拿录制成果去赌一个"进度条能拖"的功能，这个取舍不成立。
所以 `db.assembleBlob()` 在读取侧施加补丁，IndexedDB 里的分片永远保持
MediaRecorder 的原样；补丁失败最多是进度条不可拖，录制内容一定还在。

补丁打完还会**重新解析自己的输出做校验**：读不回预期时长就退回原始 Blob，
绝不交付半成品。已覆盖 25 组用例，含 SeekHead/Void 前置、Info 用多字节长度字段、
Duration 已存在且为 4 字节 float、长度字段溢出、截断头等真实形态。

### 6. 音频混流与「标签页静音」

`tabCapture` 有个副作用：一旦捕获标签页音频，用户自己就听不见了。
所以混流时要把标签页音频**回接扬声器**：

```js
const dest = audioCtx.createMediaStreamDestination();
const node = audioCtx.createMediaStreamSource(tabAudio);
node.connect(dest);              // 进录制
node.connect(audioCtx.destination); // 同时放给用户听
mic && audioCtx.createMediaStreamSource(mic).connect(dest);
```

屏幕录制**不能**这么做——系统声音再喂回系统声音会形成回环。

判断条件必须是 `isTabSource(mode)` 而不是 `mode === MODE.TAB`：区域录制本质上也是
tabCapture，同样会被掐掉原声。这里漏掉一个模式的表现是"能录，但录制期间完全听不到声音"——
纯听觉问题，读代码看不出来，所以有一组专门的音频布线测试盯着
「哪一路声音接到了扬声器、哪一路只进录制」。

### 7. 摄像头画中画：扩展源 iframe

如果在内容脚本里直接 `getUserMedia`，走的是**页面自身的源**，每个站点都会弹一次授权框。

改成往页面里插一个指向 `chrome-extension://` 的 iframe（`allow="camera"`）：
它跑在扩展源里，复用扩展已有的授权，对站点零打扰；而 `tabCapture` 录的是整个渲染结果，
气泡自然被录进成片。气泡挂在 closed shadow DOM 里，不会污染页面样式，可拖拽。

`src/content/overlay.js` · `src/camera/camera.html`

> 站点若下发 `Permissions-Policy: camera=()` 会阻断委派。这类降级**不会静默发生**：
> 注入失败时控制条会弹出「摄像头画中画未能注入，本次录制不含摄像头画面」，
> 录制元数据里的 `hasCamera` 同步置回 false，录制库上标「有降级」并可查看原因。
> 受保护页面（`chrome://`）导致倒计时无法显示时同理。

### 8. 控制界面为什么不能注入页面

`tabCapture` 会把页面里的一切都录进去——控制条注入页面就会出现在成片中。
早期版本为此单独开了一个 `type: 'popup'` 窗口，但它会一直悬在桌面上碍事，
多路并发时尤其明显。现在**扩展弹窗就是控制台**：不新开窗口，
录制状态由图标徽标承担，需要操作时点开图标。

唯一注入页面的是倒计时覆层和区域边框——前者**必须**在 `recorder.start()` 之前结束，
后者整体画在选区之外（见第 18 节）。

### 9. 停止路径收敛

停止可以由弹窗按钮、Chrome 自带的「停止共享」或关闭正在录制的标签页触发。
采集轨道结束或录制出错时，offscreen 会广播 `REC_STOPPED` 或 `REC_ERROR`。
每路录制用一个在途 Promise（`stopInFlight`）收敛重复停止，清理采集流和会话状态，
避免重复清理和重复打开播放页。关闭扩展弹窗不会停止录制。

### 10. 权限

只申请 `activeTab`，不要 `<all_urls>` ——安装时不会出现
「读取您在所有网站上的数据」的警告。覆层注入发生在用户点击扩展图标之后，
activeTab 授权已经到手。

offscreen 文档弹不出权限框，所以摄像头/麦克风由 `src/permission/permission.html`
这个真实扩展页面申请一次，授权对象是 `chrome-extension://` 源，
之后 offscreen 和 camera iframe 都能直接用。

### 11. 图标：分尺寸提示（per-size hinting）

图标不是"画一张大的然后缩放"。Chrome 工具栏实际渲染 16px（Retina 32px），
一张 128px 的精致图缩到 16px 只会糊成一团。所以 `tools/render-icons.mjs`
按尺寸走不同的绘制分支：

| 尺寸 | 画什么 | 为什么 |
|---|---|---|
| 128 / 48 | 石墨底板 + 白色屏幕轮廓 + 红色录制点 | 商店页和扩展管理页，撑得起细节 |
| 32 / 16 | 只画红色录制点，**丢掉底板** | 深色底板在深色工具栏（#202124）上等于隐形 |

红点贯穿所有尺寸，所以标识不断裂——小尺寸是大尺寸的提炼，不是另一个图标。

渲染器本身的三件事：

- **6×6 超采样**：每像素 36 个子样本，边缘是真抗锯齿，不是 alpha 斜坡糊出来的
- **超椭圆（squircle）**：`|x/a|^4.2 + |y/a|^4.2 = 1`，接近 iOS 图标的圆角手感，比纯圆角矩形更饱满
- **光源在上**：底板竖向渐变 + 顶部内高光 + 底部内暗边；红点用左上受光的径向渐变加一点高光

```bash
node tools/render-icons.mjs screen     # 生成正式图标（当前方案）
node tools/preview-sheet.mjs           # 生成 4 方案 × 4 尺寸 × 明暗工具栏对比图
```

四个候选方案（`tools/preview/icon-concepts.png`）：

| | 方案 | 取舍 |
|---|---|---|
| A | `aperture` 石墨底 + 白环 + 红点 | 经典录制键，48px 下环容易读成准星 |
| **B** | **`screen` 石墨底 + 屏幕轮廓 + 红点** | **语义最准，石墨色避开 YouTube 红，当前采用** |
| C | `dot` 纯红环 + 红点 | 各尺寸辨识度最高，但 128px 偏通用 |
| D | `crimson` 红底 + 白屏幕 | 最醒目，但 128px 观感接近 YouTube |

换方案改一条命令即可，`manifest.json` 不用动。

### 12. MP4 与格式选择

Chrome 130+ 的 `MediaRecorder` 原生支持 `video/mp4`（H.264 + AAC），所以录 MP4 不需要
任何转码环节。塞一个 25MB 的 ffmpeg.wasm 进来、还要为它把 CSP 放宽到
`wasm-unsafe-eval`，只为换个容器，不成立。

| 格式 | 编码 | 取舍 |
|---|---|---|
| MP4（默认） | H.264 + AAC | 剪辑软件 / 办公软件 / 微信都能直接吃 |
| WebM | VP9 + Opus | 同码率画质更好，体积更小 |

MP4 录制要 Chrome 130+，还依赖平台的 H.264 编码器。所以：

- **弹窗里当场探测**：用 `MediaRecorder.isTypeSupported` 逐个试候选编码器，
  不可用的格式直接置灰并写明原因，而不是让用户选完再在录制中途降级
- **真降级了就必须说**：万一探测通过但实际不可用，会退回 WebM 继续录，
  并把「当前浏览器不支持 MP4 录制，已改用 WebM」写进控制条和录制记录——
  拿到的文件后缀和预期不一样是会踩坑的
- **duration 补丁只对 WebM 生效**：那是 EBML 专用的，套到 MP4 上只会把 ISOBMFF 的盒子结构写坏

下载扩展名和按钮文案都从实际使用的 `mimeType` 反推，不写死。

### 13. 无痕模式

扩展声明为 `"incognito": "spanning"`：全局单实例、单份存储，录制分片落在**常规 profile**
的 IndexedDB 里。

这带来一个必须处理的坑：`chrome.tabs.create` 不指定窗口时会开在当前聚焦的窗口，
在无痕里录制时那就是无痕窗口——**那个上下文读不到常规 profile 的库**，
用户看到的就是「点了结束什么都没发生 / 录制库是空的」。

所以所有扩展页（播放页、授权页、控制条）都走 `openExtensionTab()`：
显式找一个 `incognito === false` 的普通窗口并指定 `windowId`；一个普通窗口都没有时
`chrome.windows.create({ incognito: false })` 现开一个。

反过来，spanning 也意味着无痕窗口里录的内容会持久化到常规录制库、不随无痕会话清除。

### 14. 徽标显示录制时长

录制中扩展图标上实时显示已录时长，暂停时徽标变灰、秒数停住。

Chrome 徽标最多约 4 个字符可读，所以按量级分段，牺牲精度换清晰：

| 时长 | 徽标 |
|---|---|
| < 10 分钟 | `0:07` `9:59`（秒级，刚开录时最需要） |
| < 1 小时 | `10m` `59m` |
| < 10 小时 | `1h05` `9h59` |
| ≥ 10 小时 | `12h`（再带分钟就超 4 字符了） |

精确到秒的时间在控制条上，徽标只负责"一眼扫到"。测试里对 24 小时内每 7 秒采样一遍，
守住"任意时刻不超过 4 字符"这个不变量。

多路并发时单路显示时长、多路显示路数，明细放进图标悬浮提示。

刷新不额外唤醒 Service Worker：offscreen 本来就每秒广播 `REC_TICK`，SW 顺带刷徽标。

**所有 `chrome.action.*` 调用都走 `safeAction()`。** 这些调用一旦同步抛错，
会把整个 `onMessage` 监听器打死，之后每一次 `REC_TICK` 都进不来，
徽标永远停在最后一个值上，而且从外面完全看不出原因。徽标是纯装饰，
任何失败都不该影响录制。同时 Service Worker 控制台会打印第一条 tick 和之后每 60 条，
用来判断这条链路是通的还是被节流了。

### 15. 导出文件名

`<标题>_<录制开始时间>.<扩展名>`，例如 `产品演示_Q3_汇报_2026-09-08_02-49-48.mp4`。
全程不含空格。

**标签页录制的标题取自页面的 `<title>`**，例如录 `AxiomOS · 目标` 这个页面就得到
`AxiomOS_·_目标_2026-09-08_02-49-48.mp4`，比笼统的「标签页录制」有信息量得多。

权限上靠 `activeTab`：用户点扩展图标那一刻，当前标签页的 `title` 就可读了，
不需要 `tabs` 权限（那会带来「读取浏览记录」的安装警告）。受保护页面、`about:blank`、
或标签页没加载完时标题为空，退回模式名。超过 80 字符截断（有些站点把整段描述塞进 title）。

屏幕录制**不**借用标签页标题——用户在选择器里选的可能是别的窗口甚至别的屏幕，
拿当前标签页的标题去命名是误导，所以保持「屏幕录制」。

**标题里不放时间戳。** 时间由两处承担：录制库列表有独立日期列，导出文件名拼 `createdAt`。
塞进标题就是三处重复，而且用户改名后仍甩不掉旧时间。

`safeFileName()` 负责清洗：**空格一律换成 `_`**（带空格的文件名在命令行、脚本、URL 里
都要额外加引号或转义，是持续的摩擦源），文件系统保留字符和控制字符同样替换成 `_`，
连续下划线收成一个，首尾的点/下划线剥掉（避免产出隐藏文件），截断到 100 字符，
全空时退回通用名。两条不变量由测试守住：**输出永不为空**、**输出永不含空白字符**。
旧版默认标题自带的 `YYYY-MM-DD HH:MM:SS` 后缀会被识别并剥掉，
所以改动之前录的内容导出时也不会出现两个时间戳。

### 16. 多标签同时录制

多路并发是贯穿式的改动，不是加个开关：offscreen 里 `sessions` 是
`recordingId -> 会话` 的 Map，每路有自己的 MediaRecorder、采集流、音频混流和写入队列；
SW 的会话状态是同构的对象，存在 `chrome.storage.session` 里（SW 重启后仍在）。

几个关键取舍：

- **一个标签页只能录一路**。对同一个 tab 再次 `tabCapture` 没有意义，而且几乎必然是误操作，
  所以直接拒绝并说明原因。不同标签页 / 屏幕 / 摄像头可以任意并发。
- **不开任何额外窗口。** 早期版本为录制中的控制单独开了一个 popup 窗口，
  多路并发时它会一直悬在桌面上碍事。改成弹窗即控制台：当前标签页那一路给大计时和
  完整控制，其他标签页每路一行、各自能暂停/结束。关掉弹窗后录制状态看图标徽标，
  再点开图标即可继续操作。
- **一个心跳服务所有会话**：offscreen 用单个 1 秒定时器广播 `{sessions:[...]}`，
  而不是每路一个定时器。
- **徽标只有约 4 个字符可读**，塞不下多路时长：单路显示时长，多路显示路数，
  明细放进图标的悬浮提示（`chrome.action.setTitle`）。
- **弹窗按标签页展示录制状态**：当前标签页显示计时和完整控制，其他录制在列表中逐路展示。
- **停止是分路的**：关闭正在录制的标签页只结束对应的录制，也可在弹窗中逐路结束或全部结束。
  每一路各有一个在途 Promise 收敛重复停止。

崩溃恢复的 `reconcileInterrupted(active)` 因此改成接受一个 id 数组——
只传单个 id 会把其他并发录制误判成「已中断」。

### 17. 截图

三种模式，都基于 `chrome.tabs.captureVisibleTab`（`activeTab` 授权即可，不需要
额外权限）。像素处理跑在 **Service Worker 里的 `OffscreenCanvas`**——SW 没有 DOM，
但有 `OffscreenCanvas` 和 `createImageBitmap`，拼接和裁剪不必再开一个 offscreen 文档。

**可见区域**：截一张，转成 Blob 入库。

**整个页面**：内容脚本量出总高并排好每一屏的滚动位置，SW 逐屏 `scrollTo` + 截图，
最后按实际滚动位置拼接。几个关键点：

- **找对滚动的是谁**。很多应用（飞书、Notion、Gmail、各种后台）是 100vh 的壳子 +
  内部滚动容器，window 一像素都滚不动，只滚 window 截出来就只有一屏。规划时先找
  `overflow-y: auto/scroll` 且基本完整落在视口里的最大容器：占视口三成以上、
  滚动距离又比 window 大，就改滚它，每一屏只裁容器的内容区（不含边框和滚动条）拼接。
  藏吸顶元素时跳过包着容器的祖先——应用壳子常常本身就是 fixed 的，藏了它后面全是白屏。
- **瞬时滚动**。`scrollTo` 一律带 `behavior: 'instant'`，否则页面的
  `scroll-behavior: smooth` 会让截图时还停在半路。
- **画布上限**。Chrome 画布单边最多 32767 设备像素，高度上限按 `devicePixelRatio`
  换算成 CSS 像素再截断，拼接时再夹一次。

- **限流**。`captureVisibleTab` 每秒最多 2 次，超了抛
  `MAX_CAPTURE_VISIBLE_TAB_CALLS_PER_SECOND quota exceeded` 而不是返回图片。
  连拍必须按 520ms 的节奏走，撞上了还要退避重试——拼到一半丢一屏，整张长图就废了。
- **吸顶元素**。不处理的话，固定导航和悬浮客服会出现在每一屏里，拼出来全是重复横条，
  这是整页截图能不能用的分水岭。第一屏保留它们（那才是页面真实的样子），之后
  `visibility: hidden`，结束时逐个还原。
- **恢复**。滚动位置、`overflow` 样式、被隐藏的元素都在 `finally` 里还原，
  中途失败也不会把用户的页面留在滚到一半、导航消失的状态。

**选定区域**：内容脚本用四块遮罩挖出选区（不是给选区加滤镜——选区内必须是原始像素），
拖拽结束后**先把覆层从页面移除、等两帧合成完成**再让 SW 截图，否则遮罩会被截进去。

**缩放换算**是最容易错的地方：选区是 CSS 像素，截图是设备像素，比例用
「实际图宽 ÷ 视口宽」算，**不直接信 `devicePixelRatio`**——页面缩放和系统显示缩放
都会让两者对不上。裁剪边界会夹紧到图片范围内，负坐标归零，零尺寸选区至少产出 1×1，
不会产生非法画布。

截图存进同一个 IndexedDB：图片是单个 Blob，但仍写进 chunks 表（seq 0），
这样 `assembleBlob` / `deleteRecording` / 存储统计都不用为图片开第二条路径。
`duration` 补丁按 `kind` 判断，图片和 MP4 都不会被 EBML 逻辑碰到。

素材库里图片用 `<img>` 渲染（长截图容器可滚），多一个「复制图片」——剪贴板只认 PNG，
JPEG 会先转一道再写。

### 18. 区域录屏

在标签页里拖拽框出一块范围，只录这块。选区覆层直接复用截图那套——两边要的东西完全一样，
没必要写第二个拖拽框。

**实现方式的选择很关键。** canvas 逐帧重绘（`drawImage` + `canvas.captureStream()`）
在这里会直接停摆：offscreen 文档是隐藏的，`requestAnimationFrame` 根本不触发。
正确做法是 Insertable Streams：

```
tabCapture 源轨 → MediaStreamTrackProcessor（拉 VideoFrame）
                → new VideoFrame(frame, { visibleRect })   零拷贝裁剪
                → MediaStreamTrackGenerator → MediaRecorder
```

Chrome 94 就有这套 API，扩展下限是 116，不需要降级路径。

三个必须处理的细节：

- **源不能降采样**。区域录制时把 `maxWidth/maxHeight` 放到 7680×4320——
  先把整页降到 1080p 再从中裁一小块，出来必然是糊的。输出尺寸由选区决定，
  本来就远小于源，编码开销不受影响。
- **`visibleRect` 必须是偶数**。I420 这类色度二次采样格式要求裁剪框的坐标和尺寸都是偶数，
  传奇数直接抛 `TypeError`，整条录制就断了。`cropBox()` 负责对齐、夹紧边界、
  保证最小 2×2，15 项测试覆盖负坐标、零尺寸、完全在画面外、帧只有 2×2 等极端输入。
- **真实分辨率要回填**。裁剪框得等第一帧才算得出来，而记录可能已经建好了。
  第一帧到达时写一次，`begin()` 再兜底写一次，保证库里显示的是真实输出分辨率
  而不是 CSS 像素的估算值。

**静止页面必须靠心跳续命。** tabCapture 是"内容有变化才出帧"的模型：源轨直接喂给
MediaRecorder 时浏览器内部会补齐时序，但经过 Insertable Streams 之后，
源不出帧生成器就一帧都没有，录出来是空文件——完全静止的页面正好命中，
表现就是"有的窗口能录、有的不能"。所以没有新帧时重发上一帧的副本；
offscreen 文档是隐藏的，定时器被钳到最小 1 秒，1fps 作为下限足够让数据持续流动，
页面一动源帧照常走主链路。

**拆管线必须是显式的，不能等读端自然结束。** 源一旦卡住（静止页面 + 采集异常），
`reader.read()` 会永远挂着，`finally` 永远不执行，心跳定时器就泄漏了：
录制早已停止，帧还在往一个没人要的轨道里写。所以 `cropVideoTrack()` 返回
`{ track, stop }`，`teardown()` 显式调用 `stop()` 清定时器、取消 reader、关闭输出轨。

**弹窗要让开，但必须等覆层真的挂上去。** 它挡着页面，而且用户拖拽的第一下点击会先被
浏览器用来关闭弹窗，结果就是"拖了但没反应"。

第一版做法是"发出 START 后定时 120ms 关窗"，这是错的：一旦注入失败或覆层没起来，
弹窗照关不误，错误连显示的地方都没有——用户看到的就是**弹窗消失了，但什么也没发生**。
而且弹窗挂着的那条消息通道同时是 Service Worker 的保活，盲目关窗把它也切断了。

现在改成握手：内容脚本把覆层挂到页面上的瞬间广播 `AREA_OVERLAY_READY`，
弹窗听到才关。在那之前 `await` 照常挂着，任何失败都能正常回到弹窗显示出来。
选择结果仍走原来的 `sendResponse`——那条挂起的调用同时给 SW 保活，
用户慢慢拖拽期间 SW 不会被回收。

**录制中的区域边框绝不能进入成片。** 我们是从选区内取像素的，画在里面就会被录进去。
所以边框整体画在选区**外面**：内边缘距选区 `REGION_GAP = 3` CSS 像素，外面再加 2px 描边，
「● 录制中」标签同样放在框外。

这里的余量不是拍脑袋定的。裁剪时坐标要向下取整到偶数设备像素（I420 的约束），
最坏情况裁剪框会比选区向外多出 2 个设备像素，换算成 CSS 像素是 `2 / scale`。
`GAP` 必须大于这个值：1x 屏时是 2px，所以 3 刚好够，高分屏更宽松。
测试直接从 `overlay.js` 里正则读出这两个常量（防止两边各改各的悄悄漂移），
扫 52212 组 `dpr × 视口宽 × 位置 × 尺寸` 组合，验证边框永远不进画面、
且裁剪永远不超出用户框选的范围——最小余量 1.60px。

**「用户取消」和「联系不上页面」必须分开。** 前者是正常流程（返回 cancelled），
后者是故障，要抛出可读错误——两者混成一个结果，用户点了开始录制什么都不发生，
又是一次无从判断的静默失败。截图的区域模式同理。

### 19. 素材库的批量操作

列表每行左侧一个复选框，选中后列表上方出现「已选 N 项 · 体积」和「下载 / 删除」两个动作；
没选任何一项时动作整组隐藏。表头的全选框有三态（全选 / 部分 / 无），Shift 点击可按范围选。

几个取舍：

- **录制中的记录不可选。** 分片还在写，既导不出完整文件，也不该被删；复选框禁用并给出原因。
- **批量下载使用 `chrome.downloads` 逐条导出，不打包 zip。** 扩展声明 `downloads` 权限，
  每条下载都等待浏览器确认完成或中断后再处理下一条，界面显示实际成功和失败的数量。
  对象 URL 在下载结束后才释放，不依赖固定延时；补查下载状态，处理小文件完成事件早于 API 返回的情况。
  重名文件自动保留不同副本，单条失败不阻断后续下载。单条下载也复用这条路径。
- **批量删除走一个 IndexedDB 事务**（`deleteRecordings`），要么全删掉要么一条不动，
  不会因为中途出错留下半截。单条删除现在也是它的特例。
- **列表行从 `<button>` 改成 `div[role=button]`。** 交互元素不允许嵌套，复选框不能放进按钮里；
  行本身保留 Enter / 空格键选中，复选框的点击不冒泡到行。
- 单条删除、录制结束后的刷新都可能让已选的 id 失效，`refresh()` 会把它们从选中集合里收敛掉。

### 20. 界面

**素材库按剪辑软件的工作区排布**：左素材面板（真实缩略图，后台逐条生成后存进记录）、中监视器
（自定义走带：时间码、逐秒跳转、全屏）、右检查器（属性、提示、导出、修剪）、底部时间轴
（标尺、V1 胶片条、A1 音频波形、播放头）。快捷键和常见剪辑软件一致：空格播放、← → 微调
（Shift 一秒）、Home / End、I / O 设入出点、M 静音、F 全屏、Esc 退出修剪。
时间轴上红色只给播放头，琥珀色只给修剪选区，两者同时出现也一眼分得开。
波形要把整条音轨解码成 PCM，十分钟以上或 150MB 以上的录像不画，只显示一条基线。
窗口窄于 1180px 时检查器叠到素材面板下面，仍然一屏放下；窄于 760px 才改成纵向滚动。

基调是**仪器面板**而不是网页表单：深色底、红色作为唯一强调色（红 = 录制）、
数字一律等宽、分组标签靠字距而不是字号拉开层级。

**令牌集中在 `src/ui/theme.css`**，弹窗和素材库共用。
按钮、下拉、录制指示灯、提示条、存储条这些
通用构件也放在这里，页面自己的 CSS 只负责排布。有一条检查扫所有页面的
`var(--x)`，确保不会引用到 theme 里没定义的令牌。

**弹窗必须一屏放下，不能滚动。** 原来是 4 个模式卡排 2×2 加 7 行整宽开关，
光这两块就 400px 打底，必然超出 Chrome 的 600px 上限。重排之后：

| 区块 | 高度 |
|---|---|
| 通电指示条 + 标题栏 | 61 |
| 页签（录屏 / 截图） | 42 |
| 模式砖（一行四个） | 69 |
| 输入源（chip 而非整行开关） | 73 |
| 旋钮区（格式 / 画质 / 倒计时，一行三个） | 75 |
| 主按钮 + 存储条 | 70 |
| **合计** | **约 402px** |

展开设备选择器 +35，出现报错 +40，最坏约 477px，仍有余量。
**没有写 `overflow: hidden`**——万一哪天算漏了，出滚动条也好过内容被裁掉看不见。

几个具体取舍：

- **设备选择器按需出现**。麦克风/摄像头没开时它不占高度，开了才滑出来。
- **输入源用 pill chip**，一行放得下三个，比三行整宽开关省 60px，
  而且按下态用红色描边，一眼能看出这次录制带了什么。
- **录制中是"表头"而不是表单**：等宽大号计时 + 呼吸的红点 + 已落盘字节数。

### 21. 修剪

**修剪（Trim）** 指在时间轴上只保留录像中连续的一段；**裁剪（Crop）** 只指画面上的区域，两个词不混用（见 [术语约定](../GLOSSARY.md)）。
入口在素材库时间轴工具栏的「修剪」（或直接按 I / O）：时间轴上出现琥珀色选区，入点把手吸附到关键帧，
「设入点 / 设出点」取播放头位置，「试看选区」只播这一段；检查器里显示入出点、保留时长、预计大小，
保存时可选「另存为新素材」或「替换原录像」（二次确认）。

**按关键帧截取，不解码、不重新编码**（为什么这么选见 [修剪架构决策](adr/0001-keyframe-aligned-trim.md)）：

- 起点往前对齐到最近的视频关键帧——普通帧只存「和上一帧的差别」，单独拿出来解不出画面。
  对齐后的实际起点实时显示在修剪条上，轨道上的细刻度就是关键帧位置；
- 终点精确截断，之后的帧直接丢掉；
- 数据全程是原分片的 `Blob.slice` 引用，只有容器头部被重写，所以 30 分钟的录像也是几秒完成。

录制策略没有改：关键帧间隔由 Chrome 决定（120+ 每 100 帧一个，画面静止时会隔得更久），
所以起点偏差一般在 0～3.3 秒。

两种容器的截法（`src/lib/trim-mp4.js` · `src/lib/trim-webm.js`）：

| | MP4（分段 fMP4） | WebM |
|---|---|---|
| 关键帧在哪 | 每个 moof 片段都从视频关键帧开始 | **不保证在 Cluster 开头**：Cluster 常常先是一个音频块，后面才是关键帧 |
| 起点 | 从关键帧片段开始；该片段里比关键帧早的音频样本丢掉 | 逐块扫描，比关键帧早的块丢掉，起始 Cluster 的块相对时间码改 2 个字节 |
| 中间 | moof 只改序号和 tfdt，mdat 原样引用 | Cluster 时间码重写，块原样引用 |
| 终点 | 重建最后一个片段的 moof/mdat，只留终点前开始的样本 | 终点之后的块丢掉 |

几个坑：

- **轨道顺序不固定。** 同一个 Chrome，有的录像 1 号轨是音频，必须按 `hdlr` 认视频轨。
- **WebM 关键帧有两种写法。** SimpleBlock 看标志位 0x80；BlockGroup 没有关键帧标志，
  没有 `ReferenceBlock` 子元素的才是关键帧。
- **时间轴以视频为准。** 录像被打断时，最后一个完整片段里的音频可能比画面长出一截，不算进时长。
- **截完必须自校验。** 产物用同一套解析器重新读一遍：从关键帧开始、视频帧数一帧不差、时长对得上，
  才交出去；否则报「修剪失败」，原录像不动。遇到不认识的结构（多个 trun、绝对 base_data_offset……）直接报错，不猜着改。

**保存是先写后删**（`db.saveTrimmed`）：新内容用新 id 完整写进 chunks，最后在一个事务里写记录——
替换时删除原录像也在这同一个事务里，中途失败原录像原封不动。替换不是原地改写，而是换了 id、
保留标题 / 录制时间 / 状态标签，这样新旧分片永远不会混在同一个 id 下被拼到一起。
两种保存方式都会先检查剩余空间（替换时新旧两份会同时在盘上）。

#### 删除中间片段并拼接

时间轴的「删除片段」打开剪辑模式：设置入出点后点击「删除选区」，可重复添加删除区间，
重叠区间自动合并。已删除的部分以斜纹标出，支持恢复和试看保留片段；保存时将剩余内容按原顺序拼接。
这与「修剪」保留一个连续选区的操作分开，编辑过程中原录像不变。

无损拼接要求每个保留片段从关键帧开始。因此删除区间的终点向后对齐到下一个关键帧，
没有后续关键帧时删除到片尾，界面显示实际范围。不能删除整条录像。

`planCuts` 先合并删除区间、计算保留区间，`cutMedia` 再处理对应容器：

- MP4 共用一个文件头，连续重排 `mfhd` 序号、平移各轨道的 `tfdt`，更新总时长。
- WebM 共用一个 Segment 和 Tracks，平移后续片段的 Cluster 时间码。
- 音视频使用同一段时间偏移，接点处丢弃越过边界的音频包，避免引入时间重叠。
- 样本仍使用原始数据切片，不重新编码；结果重新建索引，检查帧数、关键帧和总时长。

保存沿用先写后删的事务流程，记录中额外保存实际保留区间和删除区间，另存标题追加「（剪辑）」。

测试素材出自真实 Chrome 的 MediaRecorder，每个结果都交给 ffprobe / ffmpeg 独立核对
（从关键帧开始、时间从 0 起、视频帧与原片对应区间逐帧一致、能完整解码）：

测试使用 Node.js 22+。安装 ffmpeg（含 ffprobe）后可执行独立解码校验；浏览器端到端检查需要 Chrome for Testing 或 Chromium。

```bash
node tests/gen-fixtures.mjs                        # 重新录测试素材（可选，仓库里已有）
node --test tests/*.test.mjs                       # 单元 + ffmpeg 核对（没装 ffmpeg 时只跑自校验）
node tests/e2e-player.mjs "<Chrome for Testing>"   # 在真实浏览器里点一遍修剪、另存、替换、播放
```

## 已知边界

- 受保护页面（`chrome://`、Chrome 应用商店）无法注入覆层，倒计时和摄像头气泡会静默跳过，录制本身不受影响
- 共享整个屏幕时，屏幕上的扩展弹窗等可见内容也会被录进画面
- MP4 录制需要 Chrome 130+ 且依赖平台 H.264 编码器；不满足时自动退回 WebM 并明确告知
- 无痕窗口的录制会保存进常规 profile 的录制库，不随无痕会话清除
