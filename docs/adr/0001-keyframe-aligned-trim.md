# 修剪按关键帧截取，不重新编码

修剪必须在几秒内完成，即使是 30 分钟的录像也不例外，而且画质不能有任何损失。所以修剪直接截取已有的 MP4 / WebM 数据，不做解码和重新编码。起点往前对齐到最近的关键帧，终点精确截断。代价是起点不准：界面上会如实显示对齐后的实际起点，不偷偷换成别的处理方式。截取逻辑全部手写，不引入任何库，保持零构建、零依赖。

## Considered Options

- **边播放边重录**（`captureStream` + MediaRecorder）：耗时和视频本身一样长，还会多一次画质损失。
- **WebCodecs 解码再重新编码**：能精确到帧，但要写约 2000 行编解码和封装代码，耗时也是分钟级。
- **只对开头一小段重新编码，其余直接截取**：能精确到帧，但 MP4 里拼接重新编码的片段时，各播放器的兼容性不一致，成本远远大于收益。
- **引入库**：Mediabunny 一改起点就会强制重新编码；mp4box.js 只能解析 MP4；ffmpeg.wasm 有 32MB，还要放宽 CSP。

## Consequences

- 录制策略不变，没有设置关键帧间隔，关键帧间隔完全由 Chrome 决定：
  - Chrome 120+ 每 100 帧一个关键帧，画面在动时约 3.3 秒一个。
  - 画面静止时会隔得更久。
  - Chrome 116～119 的录像可能只有开头一个关键帧。
  - 所以起点偏差一般在 0～3.3 秒，最坏情况会退回开头。
- 将来如果要缩小偏差，首选是录制时设置 `videoKeyFrameIntervalDuration`。这一步曾被否决过，是为了不改变录制策略。
- 截取会重写 MP4 的文件结构，一个字段写错，整段视频都放不了。所以写完必须重新解析自己的输出做校验，校验不过就放弃这次修剪，原录像保持不动。
